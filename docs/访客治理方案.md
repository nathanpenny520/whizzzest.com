# 访客监控治理方案（2026-09-08，v1.3）

> 【统一管理说明】本方案已并入《全站优化方案》（[docs/全站优化方案.md](全站优化方案.md)）作为工作流 **W1「访客数据治理」**；排期、批次与执行状态以总纲为准，本文档继续作为 W1 的**详细分析依据**（根因排查、查询级成本、位置索引）。
> 背景：2026-09-08 发现 D1 免费额度异常——计费周期（09-05 ～ 10-05）才 3 天，Rows read 已 2.36M / 5M（47%）。
> 排查结论：大头不是公开站访客流量，而是后台「访客分析」看板的 **19+2 条全表扫描查询**，叠加近期改版引入的**默认开启的 30s 自动刷新**。
> 本方案只做策略与拆解，不含可执行代码；实施时按第七节顺序推进，数据库变更一律走迁移文件纪律。

## 一、现状数据（2026-09-08 D1 面板）

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| Rows read | 2.36M / 5M（47%） | 计费周期 09-05 起，仅 3 天；日均 ~80 万行 |
| Rows written | 14.29k | 健康远未触顶（每 PV = 1 INSERT + 1 dwell UPDATE） |
| 存储 | 1.49 MB | 极小，非问题 |
| 计费 | $0.00 | 仍在免费计划；超限不扣钱，**查询直接报错** |
| visits 表行数 | ~7k | 库 09-06 建成，增速约 2-3k 行/天（含扫描器垃圾行） |

触顶后果：免费计划超额后查询失败——主站动态路径（`/tv/*` `/library/*` `/music/*` `/attractions/*` `/merchants/*`、AI 助手）与后台全部报错，纯静态页不受影响。按当前消耗速度，**不处理约 3-4 天内触顶**；visits 表继续膨胀后，每次看板的成本还会线性上涨（估算一个月后打开一次 ≈ 300 万行读取，一次即烧光当月额度）。

面板备注：数据库卡片「Tables 0」为面板显示怪癖，可忽略；「View limits」入口可确认 5M 分母的准确口径（每日 / 每计费月），实施前先确认一次。✅ 已确认（2026-09-08）：5M 为**每计费月**额度。

## 二、根因：两条「自动」的线

### 2.1 读侧主因：后台「访客」Tab 的 30s 自动刷新（估计占比 90%+）

机制（均在 `admin/index.js`）：

- 定时器每 **30 秒**触发一次；三个条件同时满足才执行：当前视图为「访客」、自动刷新开关打开、页面处于前台可见（`admin/index.js:3125`）
- 开关「30s 自动刷新」**默认勾选**（`admin/index.js:2148`）；前端状态变量同样默认开启（`admin/index.js:2695`）
- 后台视图记忆挂在地址锚点上，重新打开后台会自动回到上次的「访客」视图（`admin/index.js:2616`）——把后台停在访客页挂着就会持续消耗
- 自动刷新为「访客分析页改版」提交（e9e8fc1）引入，此前无此消耗源

代价算术：每轮 = 19 条统计查询 + 2 条访客列表查询 ≈ 21 条，其中约 15 条为全表扫描。按当前 ~7k 行表体量，**每轮约 10-15 万行读取；前台挂机 1 小时 ≈ 1500-2000 万行**。面板已消耗的 2.36M ≈ 三天内累计打开了约 10 分钟。

### 2.2 写侧慢性问题：互联网扫描器入库

主站采集逻辑跳过自报身份的爬虫（UA 匹配 bot 规则，`worker/index.js:123`），但**不报身份的扫描器**（探测 `wp-admin`、`.env`、`.git` 等漏洞路径、落点 404 的请求）照常写入 visits，仅打 `is_bot=1` 标记（`worker/index.js:186-187`）。垃圾行不直接烧读取额度，但持续养大表，抬高每一次全表扫描的单价。

## 三、写入侧精读（`worker/index.js`）

现行流程（设计总体良好）：

1. 仅「文档导航」采集：GET 且 `sec-fetch-dest: document`（或无该头但 Accept 含 HTML）；静态资源请求不记录（`worker/index.js:118-126`）
2. 双匿名 Cookie：访客 ID（1 年）、会话 ID（30 分钟滑动）；无 Cookie 访客按 IP 归组展示
3. 每次页面浏览 1 行 INSERT，走 `ctx.waitUntil` 异步、不阻塞响应
4. HTML 响应注入回报脚本，页面关闭时 beacon 上报停留时长 → `/api/pv-dwell` UPDATE 补写（每 PV 共 2 次写）

## 四、读取侧精读（`admin/index.js` 访客模块）

每次刷新（手动或自动）实际执行的查询与真实成本：

**统计套件 19 条**（一次并发发出，`admin/index.js:485-583`），按成本分三档：

| 档 | 查询 | 成本特征 |
| --- | --- | --- |
| 全表扫描且**无时间边界**（最毒） | 每位访客首访日分布（:568）；访客列表分组统计（:630）与总数（:637） | 无论选 7 天还是 365 天，永远扫全表；列表查询还带排序 |
| 会话级聚合（贵） | 跳出率（:492）、入口页 TOP 窗口函数（:571）、会话深度（:578） | 按会话 ID 分组/排序，扫整个时间窗 |
| 维度统计（~12 条） | 日趋势 / Top 页面 / 来源 / 设备 / 浏览器 / 系统 / 语言 / 国家 / 近期浏览 / 环比 / 实时 | 有时间边界，但分组列零索引，窗口大时近似扫窗内全部行 |

**访客列表 2 条**（`admin/index.js:628-637`）：每次翻页重复执行；「总数」每次精确 COUNT 去重全表——翻 10 页扫 10 遍。

## 五、优化方案（四步，按投入产出排序）

### 第 0 步：立即执行，零改动（当天）

1. 使用习惯：打开后台后手动取消「30s 自动刷新」勾选；不看数据时不把后台停在访客视图挂机；临时需要盯实时时再开刷新
2. D1 面板「+ Add Budget Alert」设告警；「View limits」确认额度口径
3. 决策是否升级 Workers Paid（约 $5/月）作兜底——唯一「不做任何优化也立刻安全」的选项；以当前量级，付费额度下本方案第一阶段可从容排期

### 阶段一：读取侧小补丁（一次部署，预期读取量降 90%+）

目标：把「挂机烧钱」变成「按需付费」，把「全表扫」变成「范围扫」。

1. **自动刷新改造**：默认关闭；开启时拉长到 2-5 分钟；仅在数据面板可见时刷新。内部后台手动刷新完全够用（对应 R1）
2. **补时间边界**：三条无边界查询加所选时间窗下限（对应 R2）；访客「总数」改近似口径（已加载页数推算）或缓存，不再每次翻页精确数全表
3. **统计接口 60s 服务端实例缓存**：对齐主站 `handleStats` 的既有范式（对应 R6）；自动刷新与多人同开命中缓存、不碰数据库
4. **新增 (is_bot, created_at) 复合索引**：让「排除爬虫 + 时间窗」从全表过滤变索引范围扫描（对应 R3/R4）；走迁移文件纪律，编号存 `scripts/`

预期：单次刷新 10-15 万行 → 2-4 万行；挂机不再烧钱。

### 阶段二：写入侧止血（可与阶段一合并为一个小版本）

1. **扫描器不入库**：404 落点 / 扫描特征路径不再写明细，改为「每天一行的异常流量计数表」累加——保留宏观可见性（每天被扫多少次、什么路径类型），消灭几十万级垃圾明细
2. **频率熔断**：同一 IP 短窗口文档请求超阈值（如每分钟几十次）即停止写库，防恶意刷量（对应 W2）
3. **保留期清理**：主站 Worker 增加每日定时触发器（wrangler 配置加 crons，属部署配置变更），删除超 90 天明细（初始策略 90 天，可调）（对应 W3）
4. **IP 脱敏**：入库改哈希或截断；同步修正 README 的「IP 哈希」描述，使文档与实现一致（对应 W4）

### 阶段三：预聚合根治（流量增长后的终极解法，独立立项）

方向：**报表读汇总，明细只服务抽查**。

1. **日汇总表**（暂名 `visits_daily`）：每天 × 各维度值（路径/来源类型/来源站/设备/浏览器/系统/语言/国家）一行，存 PV、会话数、访客数、停留合计、跳出会话数、入口次数等加性/半加性指标。90 天趋势 = 读 90 行而非扫几十万明细——读取量降三个数量级。写入侧在回报链路顺手累加（upsert），或初期用每日定时任务从明细聚合
2. **首访登记表**（暂名 `visitors_first`）：访客 ID + 首访日期，写入侧「登记过即跳过」。每日新访客 = 按首访日期数这张小表——现状最毒的全表扫描查询（:568）从此消失
3. **口径策略**：明细表仅保留近 90 天，服务「最近浏览」「单访客轨迹」抽查；跨天去重类非加性指标（去重访客数）在长区间改用「每日访客数求和」近似口径并在界面标注；当日/近 7 天仍读明细保证精确
4. **降级预期**：90/365 天大区间视图只读汇总表；visits 行数进入「平台期」（写入 ≈ 到期清理量）

### 备选路线：Workers Analytics Engine（阶段三立项时一并评估）

Cloudflare 专为自建统计设计的绑定：写入侧换绑定调用、查询走其 SQL 接口，数据**不计入 D1 配额**，自带采样与约 90 天保留。

| 维度 | D1 预聚合（阶段三主线） | Analytics Engine（备选） |
| --- | --- | --- |
| D1 配额占用 | 汇总后极低 | 零（完全卸载） |
| 数值精度 | 精确（近似口径仅长区间去重） | 采样近似 |
| 保留期 | 自定（明细 90 天 + 汇总永久） | 固定约 90 天 |
| 查询方式 | 现有 SQL 习惯 | 需接新 SQL API |
| 改造成本 | 中（新表 + 写入侧小改 + 读取侧切数据源） | 中低（写入换绑定 + 查询重写） |

两条路线不互斥（明细留 D1、宏观趋势走分析引擎也是合法组合）。**立项时先出对比评估文档再定**，避免边写边选。

### 新增表设计要点（文字描述，实施时另出迁移文件）

- `visits_daily`：日期 + 维度列（path / kind / ref_host / device / browser / os / lang / country）+ 指标列（pv / sessions / uv / engage_sum / bounce_sessions / entry_count）；主键（日期 × 维度组合）；沿用现有「created_at 存 UTC、展示按北京时区」的口径
- `visitors_first`：vid（主键）+ first_date（北京时区日期）+ created_at
- 异常流量日计数（暂名 `scan_stats`）：日期 + 路径特征分类 + 次数 + 最近一次样本（路径 / UA 片段）；主键（日期 × 分类）
